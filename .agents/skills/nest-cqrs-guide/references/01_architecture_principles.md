# CQRS 핵심 아키텍처 원칙

- 본 문서는 NestJS CQRS 기반 메시지/핸들러/이벤트/에러 구조의 공통 표준을 정의함
- 도메인 전용 규칙이 존재하는 경우 해당 규칙을 우선 적용하고, 본 문서는 공통 원칙으로 보완함

---

## 1. 책임 분리

- **메시지 클래스**: 유스케이스의 의도와 payload를 전달하는 입력 객체로만 사용함
- **핸들러**: 유스케이스 흐름을 오케스트레이션하는 실행 진입점으로 사용함
- **도메인 규칙**: 재사용 가능한 규칙은 서비스, 헬퍼, 애그리거트 등 별도 계층으로 분리함
- **이벤트**: 이미 발생한 사실을 나타내는 결과물로 취급함
- **에러/어서터**: 정상 흐름과 분리하여 구조화된 실패 처리를 담당하게 함

## 2. 계약 명시성

- 유스케이스에 맞는 가장 작은 payload 타입을 사용함
- 경계를 넘는 흐름에서는 요청/응답 형태를 분리하여 유지함
- 메시지에 payload가 없으면 코드베이스 스타일에 맞게 명시적으로 표현함

## 3. 오케스트레이션 가독성

- 핸들러는 한 번 읽으면 흐름이 이해되도록 선형적으로 구성함
- 조회, 검증, 실행 단계를 쉽게 구분할 수 있게 배치함
- 한 파일에 서로 다른 책임을 섞지 않음

## 4. 실패 처리 구조화

- 예상 가능한 비즈니스 실패는 명시적으로 매핑함
- 어서터나 가드 로직은 필요한 유스케이스 가까이에 둠
- ad hoc 예외를 핸들러 곳곳에 흩뿌리지 않음

## 5. 이벤트 사실성

- 이벤트는 이미 일어난 일만 표현함
- 이벤트 payload는 임시 UI 상태가 아니라 지속 가능한 사실에 집중함
- 후속 사이드 이펙트는 이벤트 핸들러가 담당하고, 이벤트 정의가 담당하지 않음
